# 规范冲突检测说明

> 本文档面向系统维护者、质量工程师和知识库管理员，解释「为什么需要冲突检测、如何实现、以及每个结果的意义和处置方式」。

---

## 一、为什么航空规范知识库必须检测冲突

航空制造业的工艺规范体系具有以下特点：

1. **文档多、版本迭代快**：一家工厂可能同时维护数百份工艺规范（CPS），每年都有修订。旧版本并不总是及时作废，历史文档和现行文档共存。

2. **跨文档依赖复杂**：焊接规范会引用热处理规范，热处理规范又依赖材料规范。当上游规范更新数值时，下游引用者可能未同步。

3. **后果严重**：若一名工艺员同时参考两份对同一工序给出不同温度范围的规范，选择错误的标准可能导致零件报废甚至安全事故。

4. **人工审查代价高**：数百份文档数万个章节，依靠人工逐一比对几乎不可行。

**冲突检测的目标**：在知识图谱层自动发现「同一参数/实体在不同文档中存在矛盾定义」，将其呈现给质量工程师，以结构化方式驱动规范治理。

---

## 二、冲突的两种类型

### 2.1 约束冲突（Constraint Conflict）

**定义**：相同类型（如「焊接温度」）和单位（如「℃」）的约束参数，在不同文档中具有不同的数值或范围。

**示例**：
```
文档 CPS-1220，章节 3.2：铝合金焊接预热温度 100~120℃
文档 CPS-1440，章节 5.1：铝合金焊接预热温度 80~100℃
```

**检测方法**：纯规则，直接查询 Neo4j：
```cypher
MATCH (s1:Section)-[:HAS_CONSTRAINT]->(c1:Constraint)
MATCH (s2:Section)-[:HAS_CONSTRAINT]->(c2:Constraint)
WHERE c1.type = c2.type AND c1.unit = c2.unit
  AND s1.doc_id <> s2.doc_id
  AND c1.value <> c2.value   -- 数值不同
RETURN ...
```

**可靠性**：高（无 LLM 幻觉风险，完全基于结构化数据）

**严重度**：固定为「高危」——数值矛盾直接影响操作参数。

---

### 2.2 语义冲突（Semantic Conflict）

**定义**：两段来自不同文档、涉及同一工具/材料/工艺的章节内容，对其使用方法、适用条件或操作要求存在矛盾表述。

**示例**：
```
文档 A，章节 4.3（涉及「钛合金铣刀」）：
  "铣削前无需预涂切削液，干切即可获得最佳表面质量。"

文档 B，章节 2.1（同样涉及「钛合金铣刀」）：
  "钛合金铣削必须使用专用切削液，否则刀具寿命将降低 60% 以上。"
```

**检测方法**：LLM 辅助，两步走：
1. 从 Neo4j 中找出「同一实体节点（工具/材料/工艺）被不同文档的章节共同引用」的段落对
2. 将两段内容送给 LLM，要求判断是否存在矛盾

**LLM Prompt 结构**：
```
系统：你是航空工艺规范审核专家，判断两段内容是否存在矛盾。
用户：
  实体：钛合金铣刀（类型：Tool）
  文档 A · 章节 4.3：...
  文档 B · 章节 2.1：...
  输出 JSON: { has_conflict, severity, description, entity_in_conflict }
```

**可靠性**：中（LLM 可能误判，需人工审核确认）

**严重度**：由 LLM 输出（high / medium / low）。

## 三、系统实现架构

```
触发扫描
    │
    ├─ Phase 1: 约束规则检测
    │   Neo4j Cypher 查询约束数值矛盾
    │   → 生成 ConflictRecord（type=constraint）
    │
    └─ Phase 2: 实体语义检测
        Neo4j 查询跨文档实体共享的章节对
        ↓（每对调用一次 LLM）
        LLM 判断是否存在语义矛盾
        → 生成 ConflictRecord（type=semantic）
            │
            └─ 去重 + 写入 PostgreSQL
```

### 数据模型（`conflict_records` 表）

| 字段 | 说明 |
|------|------|
| `conflict_type` | `constraint`（约束）或 `semantic`（语义）|
| `severity` | `high` / `medium` / `low` |
| `entity_name` | 冲突聚焦的实体/约束类型名称 |
| `entity_type` | Constraint / Tool / Material / Process |
| `section_a_*` | 文档 A 侧的章节信息和内容摘要 |
| `section_b_*` | 文档 B 侧的章节信息和内容摘要 |
| `description` | 冲突描述（约束型：数值对比；语义型：LLM 一句话总结）|
| `status` | `pending` / `confirmed` / `dismissed` / `resolved` |

### 扫描性能参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `constraint_limit` | 200 | 最多返回的约束矛盾对数 |
| `entity_limit` | 60 | 送入 LLM 的实体对数（影响扫描耗时）|

扫描耗时主要取决于 `entity_limit`：60 对 × LLM 响应时间（约 1~3s）= 1~3 分钟。

## 四、在系统中使用

进入管理后台 → **规范冲突检测** 页面：

### 触发扫描

点击「开始扫描」按钮。扫描分两个阶段异步执行，进度实时展示：
- **约束规则检测**：通常秒级完成
- **LLM 语义分析**：按实体对数量线性增长，可在界面上看到进度

### 查看结果

扫描完成后，结果自动列出。可按以下维度筛选：
- **状态**：待审核 / 已确认 / 已忽略 / 已解决
- **严重度**：高危 / 中等 / 低风险
- **类型**：约束冲突 / 语义冲突

点击每条记录可展开查看两个文档的原文摘要及冲突描述。

### 处置冲突

| 操作 | 含义 |
|------|------|
| **已确认** | 该冲突真实存在，需规范修订人员介入 |
| **已忽略** | 经判断为误报（如两个文档针对不同工况）|
| **已解决** | 规范已修订，冲突已消除 |

## 五、冲突检测的局限性与改进方向

### 当前局限

1. **语义检测依赖 LLM 准确率**：LLM 可能将「适用条件不同」的两段内容误判为冲突。建议人工审核所有「语义冲突」，约束冲突可直接信任。

2. **覆盖范围受 entity_limit 限制**：为控制 LLM 调用成本，默认只检测 60 个实体对。覆盖率随参数调大而提高，但扫描时间线性增加。

3. **不检测隐含逻辑冲突**：例如「步骤 A 要求先做 X 再做 Y」而「步骤 B 要求先做 Y 再做 X」——这种顺序矛盾目前无法自动检出。

4. **约束检测依赖入库质量**：若 `Constraint` 节点在解析阶段未被正确提取（例如约束值在表格中未被识别），则无法检测。

### 改进方向

- **增量扫描**：仅对新入库文档进行扫描，而非全量扫描
- **冲突溯源**：将确认的冲突与具体的文档修订版本关联，追踪是哪次修订引入了矛盾
- **邮件/消息通知**：扫描完成后自动推送高危冲突给指定质量工程师
- **与标准规范对比**：引入行业标准（如 HB、GJB），检测企业规范与标准之间的偏差

## 六、价值总结

规范冲突检测是本系统相对于通用 RAG 平台的核心差异化能力之一：

| 维度 | 通用 RAG | 本系统（含冲突检测）|
|------|----------|---------------------|
| 知识呈现 | 按相关度召回，多源并列展示 | 主动识别矛盾，给出预警 |
| 知识治理 | 被动（用户发现问题后反馈）| 主动（系统扫描发现潜在风险）|
| 航空安全 | 无法保证来源一致性 | 提供结构化冲突报告，支持合规审计 |

对于「航空工艺规范知识库」这一特定场景，**冲突检测将系统从「信息检索工具」升级为「规范质量守门人」**。
